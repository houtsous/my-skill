# 前端开发规范

## 基本工作方式

- 在编写或修改代码前，先阅读目标项目的 `AGENTS.md`、相邻文件、目录结构、导入别名、命名方式和已有实现。
- 优先遵循当前项目已有规范；如果本技能与项目 `AGENTS.md` 冲突，以目标项目 `AGENTS.md` 为准。
- 保持改动范围与需求一致，不移动、不重命名、不格式化无关文件，不覆盖用户已有改动。
- 新文件必须放入职责明确的现有目录。只有现有目录无法表达新职责时才新建目录，新目录名称必须说明单一职责。
- 禁止为了方便创建含义模糊的 `common/`、`misc/`、`temp/`、`helpers/` 等目录或文件。
- 禁止手工修改或存放源码到 `node_modules/`、`dist/`、`out/` 等依赖或构建产物目录。

## 目录与边界

- 按项目既有分层放置代码：页面进 `pages/` 或 `views/`，复用组件进 `components/`，路由进 `router/` 或 `routes/`，状态管理进 `store/` 或 `stores/`，接口进 `api/`，非 HTTP 服务进 `services/`，工具函数进 `utils/`，常量和枚举进 `constants/`、`enum/` 或 `enums/`，类型进 `types/` 或 `api/types/`。
- Electron 项目必须区分 `main`、`preload`、`renderer` 三个运行边界：渲染进程不得直接导入 Node 模块或 `src/main/`；系统能力必须通过主进程、预加载脚本和 IPC 暴露最小接口。
- HTTP 请求不得散落在组件中；统一封装到 API 层或请求服务层。
- 状态管理模块负责客户端状态、状态变更和跨组件共享行为，不负责底层请求客户端配置。
- `index.ts` 只作为目录入口或统一导出文件，不在其中堆积具体业务实现。

## 命名规范

- 目录名称统一使用小写短横线命名；多单词目录使用 `-` 分割，例如 `menu-items/`、`ui-component/`。
- 普通文件统一使用小驼峰命名；多单词文件不得使用短横线，例如使用 `smsCode.service.ts`，不要使用 `sms-code.service.ts`。
- 只有 React 组件文件和 class 类文件使用大驼峰命名，例如 `Icon.tsx`、`RouteGuard.tsx`、`UserService.ts`。
- TypeScript 类型、接口和 namespace 使用大驼峰命名；普通变量和函数使用小驼峰命名。
- 固定值、枚举对象和枚举成员使用全大写下划线命名，例如 `APP_NAME`、`LOGIN_ROLE.ADMIN`、`SUCCESS_CODE`。
- 业务接口、服务、状态管理、枚举等普通代码文件保留项目后缀规范，例如 `userProfile.api.ts`、`smsCode.service.ts`、`routeMeta.enum.ts`。
- 类型导入使用 `import type`，除非该符号运行时确实需要。

## 类型规范

- 不要为了省略 import 把普通业务类型声明成全局类型。
- 全局类型只放真正需要全局可见的声明，例如 `Window` 扩展、Vite 环境类型、统一 API 响应结构。
- 只服务于某个 API 域的请求/响应类型必须放在该 API 域的类型文件中，不放到全局类型目录。
- 接口类型建议按领域集中，例如 `api/types/user.t.ts`，并区分 `Request`、`Response`、领域 `Info` 或响应 `Data`。
- 请求函数、运行时代码、状态逻辑不得写进类型文件。

## 接口与错误处理

- 接口文件只负责 URL、请求方法、参数组装和返回类型，不重复实现全局请求拦截、业务状态码判断和通用错误包装。
- 请求/响应拦截、统一错误提示、登录失效、业务码转换等逻辑放入请求基础设施。
- 组件和状态管理模块不直接调用 Axios；通过接口层或服务层调用。
- 接口改动必须检查 headers、异常分支、空值场景和兼容性。

## 枚举与魔法值规则

- 禁止在业务代码中散落无语义的数字、字符串、状态码、路由名、事件名、存储 key、权限 key、业务类型值。
- 遇到 `returnCode === 1`、`status === 'success'`、`type === 2`、`route.name === 'home'` 这类判断时，必须先抽成枚举或常量，再在业务代码中引用。
- 枚举或常量应放在项目现有的 `enum/`、`enums/`、`constants/` 或同等职责目录中。
- 枚举对象使用 `as const` 保留字面量类型，并导出由枚举派生的联合类型。
- 常量命名必须表达业务含义，不要只把值换个名字；例如使用 `SUCCESS_CODE`、`LOGIN_STATUS.EXPIRED`，不要使用 `CODE_1`。

反例：

```ts
if (returnCode === 1) {
  // ...
}
```

正例：

```ts
export const RESPONSE_CODE = {
  SUCCESS: 1
} as const

export type RESPONSE_CODE_VALUE = (typeof RESPONSE_CODE)[keyof typeof RESPONSE_CODE]

if (returnCode === RESPONSE_CODE.SUCCESS) {
  // ...
}
```

## 路由规范

- 每个业务路由必须有稳定的 `name`；业务判断优先使用 `name`，不要依赖容易变化的 `path`。
- 路由 `name`、菜单 key、权限 key、面包屑 key、埋点 pageName 应从统一枚举或常量中读取。
- 新增页面时同步补充路由、菜单、页面组件和必要的类型定义。
- 动态参数只作为跳转参数或查询条件传递，不替代稳定路由标识。

## 样式与界面

- 优先使用项目已有 UI 框架、主题标记、UnoCSS/Tailwind/SCSS 方案，不另起一套视觉系统。
- 共享主题变量统一维护在项目现有 `style/global/`、`style/theme/`、`theme/` 或 `themes/` 等项目现有主题目录；不要同时维护多个同义目录，例如 `theme` 与 `themes` 并存。
- 组件样式尽量靠近组件；全局样式只放基础重置样式、全局布局、主题变量和公共工具。
- 不要提交依赖生产环境的 `console.log`。
- 移动端项目需检查 rem、viewport、低版本 WebView 和宿主能力降级。

## 工程化反思

开发时不要只满足眼前功能完成。每次新增页面、接口、状态、组件、工具函数或配置时，都要主动反思：

- 是否可配置：业务值、环境值、文案、路由、权限、状态码是否可以集中配置。
- 是否可扩展：未来新增同类页面、同类接口、同类状态时是否能复用现有结构。
- 是否可复用：重复逻辑是否应抽成组件、钩子函数、组合式函数、服务、状态管理动作、工具函数或配置表。
- 是否边界清晰：接口、状态管理、组件、路由、服务、工具函数是否各司其职。
- 是否适合多人协作：命名、目录、类型和职责是否能让团队成员快速理解并减少重复造轮子。
- 是否能承载复杂业务：数据量变大、状态变多、权限变复杂、页面交互变密集时，当前设计是否还能维护。
- 是否有验证路径：改动后是否能通过类型检查、代码规范检查、构建、单元测试、页面访问或人工验证确认质量。

如果发现当前实现会把业务逻辑写死、把能力做散、或让后续同类需求复制粘贴，应优先提出更工程化的落点，再进行实现。


## 技能文件规范

- 创建或更新 Codex 技能时，必须保留 `SKILL.md` 作为核心规则文件。
- 新建技能时同时创建 `agents/openai.yaml`，用于配置界面展示名、简短描述、默认提示词和隐式调用策略。
- `agents/openai.yaml` 只放产品界面配置，不放大段业务规范；详细规则仍写在 `SKILL.md`。
- 配置文件字符串统一加双引号，默认提示词必须明确包含当前技能名，例如 `$frontend-rule`。
## 验证要求

- 完成代码修改后，按项目脚本执行对应检查，例如类型检查、代码规范检查、构建、单元测试或页面验证。
- 如果完整检查存在历史问题，至少对本次修改文件做定向检查，并在交付说明中说明未完成项和风险。
- 新增或修改依赖时，同步检查锁定文件和安全风险。
- 交付说明中简要说明改了什么、验证了什么、还有哪些边界需要后续关注。
